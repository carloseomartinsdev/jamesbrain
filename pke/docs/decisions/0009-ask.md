# 0009 — Ask Pipeline

## Storage Schema v1 — FROZEN

O schema foi estabilizado pelos Incrementos 6, 7 e 8.
A partir do Incremento 9: qualquer alteração estrutural do banco
exige migration Alembic. Alembic **não** foi instalado agora —
só entra na primeira mudança estrutural real.

`STORAGE_SCHEMA_FROZEN = True` em `pke.persist.versions`.

## Princípios

- Consulta recupera conhecimento; não completa conhecimento.
- Perguntar não altera o conhecimento consultado.
- Inferência resolve ambiguidade; não cria certeza onde ela não existe.

## Orquestração

`AskService.ask(raw, user_context, session_context) → AskResult`

Fluxo:

```
raw → Interpreter → QueryIR → ResolvedQueryBuilder
  → conceitos + entidades (QUERY) + intervalo civil
  → ResolvedQuerySpec → QueryEngine → QueryResult → AskResult
```

Ask orquestra. Não soma `Decimal`, não consulta tabelas direto,
não inventa conhecimento. O cálculo permanece no QueryEngine.

`IngestResult` não é reutilizado. Perguntar ≠ registrar.

## AskResult / status

`answered` | `needs_clarification` | `no_results` | `rejected` | `unsupported`

Campos: `query_result?`, `resolved_spec?`, `issues[]`, `clarification?`,
`resolved_entity_ids[]`. Sem frase de UI.

- consulta válida sem fatos → `no_results` (não `rejected`, não `R$ 0,00`)
- conceito/kind/IR/isolamento/multi-currency → `rejected`
- IngestIR enviado a Ask → `unsupported`
- falha de Interpreter → `rejected`
- entidade inexistente (nome) → `no_results`
- entidade ambígua → `needs_clarification` (`clarify.entity.which_one`)
- ID estrangeiro → `rejected` (sem vazamento)

## QueryIR

Expressa menções, associação, tipos/ações/fatos, aggregate,
expressão temporal estruturada, hierarchy/version/currency/sort.
Interpreter **não** inventa IDs persistentes.

## Resolução QUERY

`ResolutionPurpose.QUERY`: `create_candidate` proibido;
nenhuma Entity materializada; nenhum alias aprendido;
PersonalContext persistente não muda por perguntar.

`ResolutionPurpose.INGEST` permanece o default da ingestão.

## Query Temporal Resolver

`QueryTemporalResolver` ≠ `TemporalResolver` de eventos.

Entrada: `IrQueryTime` já estruturada + relógio injetado +
`UserContext.timezone`. Saída: `AbsoluteRange` civil `[start, end)`.
Não parseia português. Não usa timezone da máquina.

Períodos: `this_month`, `last_month`, `this_week`, `last_week`,
`today`, `yesterday`, intervalo explícito datetime, intervalo
explícito date.

### Contrato de ranges de data (congelado)

O QueryEngine só recebe `[start, end)` absoluto. Não interpreta linguagem.

| Camada | Contrato |
|---|---|
| datetime boundary | `IrQueryTime.start` / `end` já são o intervalo de execução |
| civil date boundary | `date_from` inclusivo; `date_to` = `T00:00` exclusivo. `date_to=2026-09-03` → o dia 03 **não** participa |
| intervalo linguístico inclusivo | “de 1 a 3 de setembro” (três dias civis) chega como `date_from=2026-09-01`, `date_to=2026-09-04` → `[2026-09-01T00:00, 2026-09-04T00:00)` |

A expansão linguística → `date_to` exclusivo é do Interpreter.
`QueryTemporalResolver` só materializa o contrato estruturado.

Períodos relativos usam a **data civil no timezone do usuário**, não o
mês UTC nem o timezone da máquina. `2026-09-01 15:00` Fortaleza **não**
cai em agosto em Honolulu; o cruzamento de mês exige instante cedo o
bastante (ex.: `05:00` Fortaleza → `22:00` de 31/08 em Honolulu).

### Semana (pt-BR)

Política `WeekStart.MONDAY` (configurável; default segunda).
Terça 01/09/2026 → `this_week` = [31/08 00:00, 07/09 00:00).

## “Quanto gastei”

O Interpreter produz SUM + `attribute.amount` +
`event.vehicle_maintenance` para o Caso F.
`amount` **não** é sinônimo universal de gasto.
Ontologia financeira completa fica para evolução posterior.

## Read-only

`AskService.ask` não grava conhecimento, não cria `RawInput`
da pergunta, não aprende alias. Pergunta ≠ conhecimento.
